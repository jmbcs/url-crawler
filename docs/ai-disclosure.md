# Tooling and AI disclosure

The tooling, the sources consulted, what AI drafted, and how its output was verified. The exercise
asks for this in detail, so it is a page rather than a sentence.

## IDE and local tooling

- **Editor and AI**: Visual Studio Code, used as an editor only, no Copilot or inline completion.
  Every AI interaction ran through Claude Code in its integrated terminal, the only AI in the workflow.
- **Tooling**: Python 3.12 (`.python-version`), `uv` with the committed `uv.lock`, `ruff` for lint
  and format, `mypy --strict` over `src/` and `tests/`, `pre-commit` running both on every commit,
  `make check` as the local gate and GitHub Actions as the remote one.
- **Service extras**: Docker Compose for a local Postgres, Alembic for the schema, migrations
  autogenerated and never hand-edited.

## Learning the subject

Sources consulted during the design discussion and while implementing, each with the question it
answered:

- httpx docs, on transports/redirects/timeouts: how `follow_redirects=False` interacts with
  `Location`, what `Limits` bounds, why the four timeout phases are set separately.
- The httpx exception hierarchy, in source: which exceptions are worth retrying, and that
  `UnsupportedProtocol` and `LocalProtocolError` sit under `TransportError` next to retryable leaves.
- selectolax/lexbor docs: how a real HTML5 parser recovers from malformed markup, and whether
  adoption-agency reconstruction duplicates an anchor (`unclosed_anchor.html` pins the answer).
- RFC 9110 section 10.2.3, on `Retry-After`: both accepted forms, delta-seconds and HTTP-date.
- RFC 9309, on robots.txt: matching rules (2.2, not in the standard library) and why a 5xx blocks
  the crawl (2.3.1).
- Heydon and Najork, "Mercator: A Scalable, Extensible Web Crawler" (1999): the per-host frontier
  argument in [extending.md](extending.md).
- PostgreSQL docs on `FOR UPDATE SKIP LOCKED`: the crawl service's claim query and the multi-domain
  batch claim.
- SQLAlchemy 2.0 and Alembic docs: how `run_sync` drives a migration on an async driver, and what
  `alembic check` compares.

## Interactive AI and the multi-agent workflow

- The only interactive AI was Claude Code in a terminal, used conversationally throughout: design
  discussion first, then implementation, then this documentation.
- Architect agents proposed candidate architectures, critic agents attacked them, judge agents
  scored the comparison, writer agents each implemented one module against a shared interface
  contract, and reviewer agents checked the result.
- I reviewed and approved the design document and every decision in
  [design-decisions.md](design-decisions.md), and approved the interface contract, before any code
  was written. The crawl service went through the same loop a second time, with its own contract.
- **Where the process caught itself**: an early pass classified retryable errors with
  `isinstance(exc, httpx.TransportError)`; the critic caught that `UnsupportedProtocol` and
  `LocalProtocolError` are also `TransportError` subclasses, which would have retried caller bugs.
  The code enumerates the retryable leaves instead, pinned by `tests/unit/test_retry.py`.
- The same panel wrote dependency pins from memory; the critic flagged two as stale, thrown out in
  favor of pins from `uv lock`.

## What AI drafted and what was written by hand

- Claude Code drafted every file here (packages, tests, fake site, benchmark, this documentation);
  my contribution was direction and judgement: framing the exercise, picking one of three candidate
  architectures, settling the four interpretation calls, and accepting or rejecting each decision.
- **Read in full**: the design document, the interface contracts the writer agents worked from,
  every design decision in [design-decisions.md](design-decisions.md), and the crawl contract the
  fake site pins.
- **Spot-checked, not read line by line**: module implementations, checked against those four
  sources; the test suite, ruff and mypy carry the rest.

## How AI output was verified

Nothing here is claimed on the strength of a model having said it.

- Behaviour is asserted by the test suite: 676 tests across the layers in [testing.md](testing.md),
  of which 80 need a Postgres (`make test`, then `make db-up && make test-service`), plus one
  network smoke test deselected by default. The crawl contract, the retry table, the scope
  near-misses, the exit codes, and the claim/heartbeat/reaper transitions are test-enforced, not
  described.
- Dependency versions come from `uv lock`, committed rather than typed from memory; the httpx
  exception hierarchy was checked against the library, which is how the `TransportError` mistake
  was caught.
- The speed table is a measured `make bench` run on the machine named in it, repeated once to check
  reproducibility, with the concurrency-40 point added by hand to find where the curve bends.
- `ruff check`, `ruff format --check` and `mypy --strict` run over `src/` and `tests/` (pre-commit
  locally, the `lint`/`types` jobs in CI); `alembic check` in the service suite fails if the
  committed migration and the models disagree.
- The unclosed-anchor parser fixture exists because the behaviour was an inference: the test records
  what lexbor actually does.
